# 全量积压处理与矩阵修复

2026-11-02，按用户要求处理所有现有积压，而不是将候选一律标为批准。

## 全量处理实测

开始时总计443条候选：400条未处理，6条原失败记录重试一次。`scripts/process_backlog.py` 通过运行中的 API 分批处理并保存每个批次记录。

结束时：194条 completed、211条 skipped、38条 failed，合计443条；未处理为0。错误与跳过理由保留在每条候选上，未虚构通过状态。API 的 pending 仍表示历史的未登记审核字段，不等同于未处理；页面积压统计改用 unprocessed。

数据库最终有398条带来源的事件记录。这是按来源提取的记录数，同一进展可能被多篇报道覆盖，不是398条去重新闻或398项商业部署。结构化实际运行记录见 `backlog-processing.json`；其中包含真实 API / token 用量，不推算或编造费用金额。

## 行业地图问题与修复

原页面只读取前200条事件，把所有公司与每条原始标签交叉铺开，产生大量空格。

修复为读取全部分页、只默认展示有事件记录的企业，并将原始标签映射为稳定的浏览方向。点击有记录的单元格可展开真实事件并查看原文证据；无记录显示“暂无该方向记录”，不推断企业不具备能力。

使用页面相同分类函数对真实 API 数据核对：398条事件、25家有记录企业、11个浏览方向、119个非空单元格。分类是浏览辅助，不是能力评分。

## 产品能力矩阵问题与修复

企业事件与产品 Claim 不是同一种数据。自动采集新 Snapshot 后，如果还没有该快照的 Claim，原对比接口会返回空格。初次核对时当前 Claim=0。

已通过既有任务队列给三个原产品的最新快照补算 Claim，补充了产品关联来源自动入库时同步提取 Claim 的逻辑。未分析快照现在明确显示“最新快照待分析”，不再混同“证据不足”。

同时修复了证据验证器的全页限定词误判：长 README 的其他章节出现 Demo，不应该让无关功能全部验证失败。现在检查证据附近上下文，仍拒绝把证据附近的演示/计划描述当成已发布。补充相应回归测试。
